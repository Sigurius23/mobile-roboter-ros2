WHY NO SYNCHRONIZER

A slow sensor never holds back a fast one, and no message is thrown away. KeepLast(10) + reliable: a short delay costs no measurements.

Next come the TF objects. The broadcaster publishes our result, the robot’s pose; other programs like RViz read it from TF. In C++, make_shared creates the object and a pointer to it that cleans up after itself. The buffer and the listener belong together: the buffer stores every transform it has heard about, and the listener subscribes to /tf and /tf_static and fills it. We need them because TASK 1 asks this buffer how each sensor is mounted. Then the subscriptions. create_subscription tells ROS: call me when a message arrives on the odom topic, and the function it calls is odomCallback. std::bind packs that member function together with this object so ROS can call it. Keep last ten means up to ten messages wait if the callback is busy; reliable means none get lost. The same follows for the IMU and the lidar scan. Why not wait for all three together, like the synchronizer in Exercise 4? Because then a slow sensor holds back a fast one, and messages that don’t fit get thrown away. Possible question: why a class instead of globals? The node’s memory stays together and private, callbacks become member functions that can reach it, and it’s the usual ROS 2 style.
