The initial guess: where ICP starts looking

double vx = state_.x(3); // speed v
double w  = state_.x(4); // turn rate ω

guess_robot_base(0) = vx * dt_scan; // forward [m]
guess_robot_base(1) = 0.0;         // sideways [m]
guess_robot_base(2) = w * dt_scan;  // turn [rad]

C++

state_.x(3) is entry 3, counting from 0: x, y, θ, v, ω, a.

WHY FROM THE FILTER

It combines wheels, gyro and ICP: the best estimate of the current motion. Raw wheels would carry slip in turns.

WHY SIDEWAYS 0

Wheels can’t slide sideways; on a curve the offset is ≈ v·dt·sin(ω·dt/2), under 1 mm at 20 scans per second.

WHY NO ACCELERATION

Over 50 ms, ½·a·dt² adds less than a millimetre.

TASK 2 comes right after TASK 1, still inside scanCallback. The new scan is now in the robot frame. Next, ICP in TASK 3 will shift the old scan until it lines up with the new one, and TASK 2 decides where that search starts. Why does the start matter? ICP only finds the nearest fit; if it starts far away from the real motion, it can lock onto the wrong fit. The guess starts from the Kalman filter’s state. Entry three is the speed and entry four is the turn rate; C++ counts from zero, so entry zero is x. We take them from the filter rather than from the raw wheels, because the filter combines wheels, gyroscope and ICP, so it’s our best estimate of how the robot is moving. The forward part is speed times the time since the last scan; with a scan every fifty milliseconds that’s about six and a half centimetres. We ignore the acceleration, because over fifty milliseconds it adds less than a millimetre. The sideways part is zero, because wheels can’t slide sideways. The turn is the turn rate times the time since the last scan. Testat question: why does pure-ICP mode start at zero? With icp_only the filter doesn’t run, so x(3) and x(4) stay zero, and ICP has to find the whole motion itself.
