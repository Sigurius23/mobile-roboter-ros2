A KNOWN WEAKNESS · NOT FIXED, BUT WORTH KNOWING

No predict before the ICP correction

// odomCallback, line 221: predict first, then correct
state_ = predict(state_, dt);

// scanCallback, line 396: straight to the correction
auto res = icp(last_cloud_base_, cloud_in_base, guess);

// the fix: before the correction
state_ = predict(state_, (stamp - filter_time_).seconds());
filter_time_ = stamp;

WHAT HAPPENS

ICP corrects the state of the last odom or IMU message, a few milliseconds before the scan.

WHY IT BARELY MATTERS

The gap is a few ms (odom 50 Hz, IMU 125 Hz), and ICP measures speeds, which hardly change in a few ms.

Every odometry and IMU callback calls predict before it corrects. The scan callback doesn’t. So ICP corrects the state of the last odometry or IMU message, a few milliseconds before the scan was taken. In the odometry callback, predict moves the state to the message’s time before the correction. In scanCallback, the correction starts right after ICP, with no predict in between. Strictly, it should first predict to the scan’s time stamp and update filter_time_. Why it barely matters here: the gap is at most a few milliseconds, because odometry and IMU arrive fifty and a hundred and twenty five times a second. And ICP measures speeds, not a position, and a speed hardly changes in a few milliseconds, so the error is tiny. If you’re asked, name the fix: predict to the scan’s time first.
